                                            Решение: перенос docker-compose на сервер

  Ниже пошагово описано, как настроить деплой так, чтобы docker-compose.yml и .env лежали на сервере, 
а GitLab Runner только доставлял обновления и перезапускал контейнеры.

1. Создайте директорию на сервере
Выберите постоянное место, например /opt/technical-helper:

bash
sudo mkdir -p /opt/technical-helper
sudo chown $USER:$USER /opt/technical-helper   # или под вашего пользователя

2. Положите туда docker-compose.yml
Скопируйте текущий docker-compose.yml из репозитория на сервер. 
В дальнейшем он будет обновляться автоматически при деплое, но можно и вручную.

3. Создайте .env файл
В этой же директории создайте .env с нужными переменными:

bash
cd /opt/technical-helper
nano .env
Пример содержимого:

text
DB_PASSWORD=secret
API_KEY=12345
Установите права, чтобы только владелец мог читать:

bash
chmod 600 .env

4. Измените .gitlab-ci.yml в репозитории
Теперь деплой должен:

скопировать обновлённый docker-compose.yml (и другие файлы, если нужно) на сервер;

затем по SSH выполнить docker-compose в директории /opt/technical-helper.

Пример джобы в .gitlab-ci.yml:

yaml
deploy:
  stage: deploy
  only:
    - main
  script:
    # Копируем docker-compose.yml на сервер (замените user@server)
    - scp docker-compose.yml user@your-server:/opt/technical-helper/
    # Дополнительно можно скопировать весь проект, если нужно
    # - rsync -avz --delete ./ user@your-server:/opt/technical-helper/
    
    # Заходим по SSH и перезапускаем контейнеры
    - ssh user@your-server "cd /opt/technical-helper && docker-compose pull && docker-compose up -d"
Если вы используете SSH-ключи для доступа, убедитесь, что они настроены в GitLab Runner (переменные SSH_PRIVATE_KEY и т.п.).

Важно: в docker-compose.yml не должно быть жёстко прописанных секретов – используйте подстановку из .env (синтаксис ${VAR_NAME}).

5. Проверьте работу
Вручную выполните на сервере:

bash
cd /opt/technical-helper
docker-compose up -d
Убедитесь, что контейнеры поднялись и переменные подхватились.

6. Обновление .env вручную
Теперь вы можете в любой момент зайти на сервер, отредактировать .env и перезапустить контейнеры:

bash
cd /opt/technical-helper
docker-compose up -d --force-recreate
При этом репозиторий и пайплайн не затрагиваются.

                                    Альтернативный вариант (если менять деплой нельзя)

  Если по каким-то причинам нельзя изменить способ запуска docker-compose (например, он должен выполняться на машине раннера), 
можно рассмотреть такие обходные пути:

Хранить .env в GitLab CI/CD Variables – тогда переменные будут доступны в джобе, 
но менять их придётся через веб-интерфейс GitLab, а не на сервере.

Использовать Docker Secrets или Configs – для Swarm, но это усложнит конфигурацию.

Монтировать файл с переменными с сервера в контейнер раннера – например, через NFS или sshfs, но это ненадёжно.

Однако наиболее правильное и простое решение – перенести выполнение docker-compose на сам сервер, как описано выше. 
Это стандартная практика для production-деплоя.

                                                        Резюме
                                                        
Чтобы иметь .env на сервере и не трогать репозиторий, нужно:

Создать постоянную директорию на сервере.

Хранить там docker-compose.yml и .env.

Настроить GitLab CI так, чтобы он копировал обновлённые файлы на сервер и запускал docker-compose по SSH.

Тогда вы сможете редактировать .env на сервере в любое время, а GitLab будет отвечать только за доставку кода и перезапуск.


--------------------------------------------------------------------------------------------------------------------------------

                                    Использование GitLab Runner непосредственно на сервере

  Если на вашем сервере Yandex Cloud установлен и зарегистрирован GitLab Runner, 
задача упрощается — переменные CI/CD автоматически доступны в окружении раннера. 
Тогда можно просто выполнить:

yaml
deploy:
  stage: deploy
  script:
    - export HOST_SERVER_IP=$HOST_SERVER_IP
    - docker-compose up -d

Но если раннер работает на том же сервере, где разворачивается приложение, и имеет доступ к Docker, это самый простой путь.

Если на удалённой машине присутствует файл .env с такой же переменной - её нужно удалить !!!

----------------------------------------------------------------------------------------------------------------------------------

                                              Рекомендации по безопасности

Используйте masked variables в GitLab, чтобы значение не отображалось в логах.

Для продакшена настройте protected variables или environment scopes, чтобы переменная была доступна только для определённых веток/окружений.

SSH-ключи для деплоя храните в GitLab CI/CD Variables (например, SSH_PRIVATE_KEY) и добавляйте в ssh-agent.

Убедитесь, что на сервере нет устаревшего .env с этим значением — удалите его, если он больше не нужен.
