1. KAFKA_NODE_ID: 2

Что делает:  Задаёт уникальный идентификатор узла (брокера/контроллера) внутри кластера.

Зачем нужен: В KRaft каждый узел (брокер и/или контроллер) должен иметь уникальный node.id. 
             Он используется для идентификации в кластере, при выборах контроллера, 
             в метаданных и в списке controller.quorum.voters. 
             Здесь 2 означает, что это второй узел кластера.

----------------------------------------------------------------------------------------------------------

2. KAFKA_PROCESS_ROLES: broker,controller

Что делает:  Указывает, какие роли выполняет данный процесс Kafka.

Зачем нужна: В KRaft узел может быть только брокером (broker), только контроллером (controller) 
             или совмещать обе роли (broker,controller). 
             В данном случае узел является и брокером (хранит партиции, обслуживает продюсеров/потребителей), 
             и контроллером (участвует в управлении метаданными кластера).

Важно:       Для production-сред обычно рекомендуется разделять роли, но для локального/dev-окружения совмещение допустимо.

----------------------------------------------------------------------------------------------------------

3. KAFKA_LISTENERS: PLAINTEXT://:9092,CONTROLLER://:9093

Что делает:   Определяет адреса и протоколы, на которых процесс Kafka будет слушать входящие соединения.

Зачем нужна:  PLAINTEXT://:9092 — слушатель для клиентского трафика (продюсеры, потребители, административные запросы). 
              Порт 9092 внутри контейнера.
              CONTROLLER://:9093 — слушатель для взаимодействия между контроллерами (в KRaft контроллеры общаются по отдельному каналу).

Формат:       имя_протокола://хост:порт. Пустой хост : означает привязку ко всем интерфейсам контейнера.

----------------------------------------------------------------------------------------------------------

4. KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://localhost:9094

Что делает:   Указывает адрес, который брокер будет сообщать клиентам (продюсерам, потребителям) для подключения.

Зачем нужна:  Когда клиент подключается к брокеру (например, через bootstrap.servers), 
              брокер возвращает этот адрес, чтобы клиент мог установить соединение с нужной партицией.

Важный нюанс с Docker:  Внутри контейнера брокер слушает порт 9092, 
                        но на хост-машине этот порт проброшен как 9094 (см. ports: - "9094:9092"). 
                        Поэтому advertised.listeners должен указывать localhost:9094, 
                        чтобы клиенты с хоста могли корректно подключиться. 
                        Если бы указали localhost:9092, клиент попытался бы подключиться к порту 9092 на хосте, 
                        который не проброшен (или занят другим брокером).

----------------------------------------------------------------------------------------------------------

5. KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER

Что делает:   Указывает, какой из объявленных слушателей (listeners) используется для обмена данными между контроллерами.

Зачем нужна:  В KRaft контроллеры общаются между собой (для репликации метаданных, выборов лидера). 
              Эта настройка связывает логическое имя CONTROLLER с соответствующим слушателем, объявленным в listeners.

----------------------------------------------------------------------------------------------------------

6. KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: CONTROLLER:PLAINTEXT,PLAINTEXT:PLAINTEXT

Что делает:   Определяет протокол безопасности для каждого имени слушателя.

Зачем нужна:  Здесь оба имени (CONTROLLER и PLAINTEXT) используют протокол PLAINTEXT (без шифрования и аутентификации). 
              В production обычно для контроллера и клиентов настраивают SSL/SASL.

Формат:       имя_слушателя:протокол_безопасности.

----------------------------------------------------------------------------------------------------------

7. KAFKA_CONTROLLER_QUORUM_VOTERS: 1@kafka-1:9093,2@kafka-2:9093,3@kafka-3:9093 

Что делает:   Перечисляет всех узлов-контроллеров (голосующих) в кластере KRaft.

Зачем нужна:  Это список участников кворума контроллеров. Каждый контроллер должен знать о других, 
              чтобы формировать кворум и выбирать активного контроллера. 
              Формат: id@host:port, где host:port соответствует контроллерному слушателю (CONTROLLER://:9093).

Важно:        Этот список должен быть одинаковым на всех узлах кластера. Здесь все три узла являются контроллерами.

----------------------------------------------------------------------------------------------------------

8. KAFKA_INTER_BROKER_LISTENER_NAME: PLAINTEXT

Что делает:   Указывает, какой слушатель используется для обмена данными между брокерами (репликация партиций).

Зачем нужна:  Когда брокеры реплицируют данные, они подключаются друг к другу по этому слушателю. 
              В данной конфигурации используется тот же PLAINTEXT слушатель (порт 9092 внутри контейнера).

Примечание:   В production часто выделяют отдельный слушатель для межброкерного трафика, чтобы изолировать его от клиентского.

----------------------------------------------------------------------------------------------------------

9. KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 3

Что делает:   Задаёт фактор репликации для внутреннего топика __consumer_offsets.

Зачем нужна:  Этот топик хранит оффсеты потребительских групп. 
              Чтобы обеспечить отказоустойчивость, его реплики должны быть распределены по нескольким брокерам. 
              Значение 3 означает, что каждая партиция будет иметь 3 реплики (на трёх брокерах).

Важно:        Должно быть ≤ количества брокеров. Так как у нас три брокера, 3 — корректно.

----------------------------------------------------------------------------------------------------------

10. KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: 3

Что делает:   Задаёт фактор репликации для внутреннего топика __transaction_state.

Зачем нужна:  Этот топик используется для хранения состояния транзакций (при использовании exactly-once семантики). 
              Репликация обеспечивает сохранность этих данных.

Важно:        Также должно быть ≤ числа брокеров.

----------------------------------------------------------------------------------------------------------

11. KAFKA_TRANSACTION_STATE_LOG_MIN_ISR: 2

Что делает:   Минимальное количество реплик, которые должны подтвердить запись (in-sync replicas) для топика транзакций.

Зачем нужна:  Это параметр надёжности. Если число синхронизированных реплик опускается ниже 2, 
              брокер перестанет принимать записи в этот топик, чтобы избежать потери данных.
              Значение 2 означает, что как минимум две реплики (включая лидера) должны быть в sync. 
              При трёх брокерах это разумный компромисс между доступностью и надёжностью.

----------------------------------------------------------------------------------------------------------

12. KAFKA_GROUP_INITIAL_REBALANCE_DELAY_MS: 0

Что делает:   Устанавливает задержку перед первой ребалансировкой потребительской группы.

Зачем нужна:  По умолчанию Kafka ждёт 3 секунды перед тем, как запустить первую ребалансировку, 
              чтобы дать потребителям время присоединиться. 
              В dev-средах часто ставят 0, чтобы ускорить запуск и тестирование.
              Значение 0 означает отсутствие задержки — ребалансировка начнётся сразу после присоединения первого потребителя.

----------------------------------------------------------------------------------------------------------

13. KAFKA_NUM_PARTITIONS: 3

Что делает:   Задаёт количество партиций по умолчанию для новых топиков, создаваемых без явного указания.

Зачем нужна:  Когда администратор создаёт топик без параметра --partitions, Kafka использует это значение. 
              Здесь 3 означает, что по умолчанию топики будут иметь 3 партиции, 
              что позволяет распараллелить обработку и использовать все три брокера.

----------------------------------------------------------------------------------------------------------

Общие замечания

*   Все переменные с префиксом KAFKA_ автоматически преобразуются Docker-образом в свойства конфигурации Kafka: 
  KAFKA_NODE_ID → node.id, KAFKA_LISTENERS → listeners и т.д. Это стандарт для официального образа apache/kafka.

*   Некоторые параметры (например, 
  KAFKA_CONTROLLER_QUORUM_VOTERS, KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR, 
  KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR) 
  должны быть одинаковыми на всех узлах кластера для корректной работы.

*   Приведённая конфигурация рассчитана на локальный запуск кластера из трёх брокеров с совмещёнными ролями, 
  что удобно для разработки и тестирования, но не рекомендуется для высоконагруженных production-систем.
